01 / PROBLEM

Why test the application, not just the model?

LLM applications combine model responses with application instructions, retrieved content, access controls and external tools. A model's behavior in a conversation is not sufficient evidence that the complete system respects its security boundaries.

This project explores a practical audit question: Can a controlled testing process reveal instruction-following failures and sensitive-information disclosure without mistaking an ambiguous answer for a confirmed vulnerability?

01Authorized scope

Local or explicitly permitted targets only; the prototype is not an Internet scanner.

02Evidence-driven verdicts

Scenario-specific checks distinguish proven failures from uncertainty and technical errors.

03Synthetic data

Test content and canary markers are fictitious; no production secrets are needed.

02 / SYSTEM DESIGN

A separate audit engine and local target.

The implementation distinguishes UniAssist, a fictional university chatbot used as a test target, from the independent audit engine. UniAssist is not the name of the overall Red Team project.

Target application

A FastAPI endpoint orchestrates requests to a local Ollama model. Its context uses invented university data and controlled markers to probe confidentiality behavior.

Audit engine

Scenario validation, HTTP execution and per-scenario evaluators separate attack delivery from evidence assessment. Requests are tracked rather than silently retried.

Evidence outputs

Development branches implement structured JSON and JSONL results and a standalone HTML report. A technically failed request is classified as an error, not a vulnerability.

Experimental extensions

Adaptive variants, an installable CLI, optional attacker-LLM follow-ups and a local dashboard exist on development branches. They are not presented as a finished public release.

What the disclosure does—and does not—show.

Reproduction of a canary placed inside the model's context demonstrates a disclosure weakness in that test configuration. It does not establish access to an unrelated private file, exfiltration from a production system, or the effectiveness of the entire future audit engine.

Verdict discipline

PASS and FAIL require scenario-specific evidence; INCONCLUSIVE is reserved for ambiguous responses, and ERROR for failed requests. An absent canary does not prove universal safety.

Reproducibility

Testing uses synthetic context, explicit scenario identifiers, HTTP requests and response traces. Broader conclusions will require manually reviewed examples and repeatable runs.
