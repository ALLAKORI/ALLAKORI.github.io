Scope and evidence standards

This manual is a companion to the interactive command generator. It is not a checklist guaranteeing domain compromise. Every claim should connect to a tested prerequisite, an observable result and a reversible change wherever possible. The generator includes 44 syntax-reviewed templates; they are not all end-to-end target-tested. Commands and flags vary with installed tool versions.

Only use controlled labs or explicitly authorized assessments. Do not upload actual domain credentials, tickets, private infrastructure inventories or victim data to a public portfolio. Shell arguments and history may expose passwords even if a webpage stores nothing.

01 / The investigation loop

Recon → Identity → Reachability → Directory and shares → Graph → Effective permissions → Hypothesis → Validation → Evidence → Reassess. Repeat when your access or observed controls change.

02 / Protocol and identity groundwork

Distinguish the NetBIOS domain, DNS realm, DC FQDN and host FQDN. Kerberos requires correct naming and acceptable time skew. An LDAP RootDSE response can be available even when anonymous directory searches are denied. SMB null, guest and empty credentials are not interchangeable.

nmap -Pn -sV -p 53,88,135,139,389,445,464,636,3268,3269,5985,5986 10.10.11.42
ldapsearch -LLL -x -H ldap://10.10.11.42 -s base -b "" defaultNamingContext
nmap -Pn -p445 --script smb2-security-mode 10.10.11.42

Replace the IP with your authorized target. Read-only discovery must still respect scope and rate limits. User lists, SPNs, LDAP attributes, SYSVOL, NETLOGON, password-policy and trust metadata should be recorded with their source and the exact account used.

03 / Effective AD permissions and graph reasoning

BloodHound CE expresses potential relationships, not guaranteed exploitability. Validate the principal, target object, inherited/explicit ACE, write scope and all practical preconditions before mutating a directory object.

PermissionMeaning in practiceVerification question
GenericAll / GenericWriteBroad or scoped control over an object/attributesWhich attributes actually accept your writes?
WriteDACL / WriteOwnerChange authorization entries or ownershipAre inherited restrictions or object protections relevant?
ForceChangePasswordReset another account's passwordIs the right effective on this specific user?
WriteGPLinkModify linked GPO references on the target OU/domainCan you link an existing applicable GPO, and do you control its settings and scope?
WriteMembers / AddMemberAlter membership of a specific groupAre privileged group membership changes actually allowed?

GPO investigations need gPLink, gPOptions, OU inheritance, security filtering, WMI filtering, computer/user configuration, and SYSVOL/GPC consistency. A visible graph edge without effective policy application is not enough.

04 / Kerberos, tickets and delegation

Track credential material separately: plaintext password, NT hash, AES key, ccache, kirbi, TGT and service ticket. Determine the target SPN, whether the principal can request the ticket, whether impersonation is permitted, and what authentication mechanism is accepted by the target service.

S4U and delegation decision tree

Unconstrained delegation: evaluate the actual service principal, machine configuration and exposure of delegated TGTs. Constrained delegation: inspect msDS-AllowedToDelegateTo, protocol transition and service-class restrictions. RBCD: inspect msDS-AllowedToActOnBehalfOfOtherIdentity and the identity that can update the resource object's security descriptor. PKINIT: verify KDC certificate availability and effective certificate mapping before assuming it is usable.

AS-REP roasting and Kerberoasting are conditional credential-auditing paths, not universal first steps. Keep lockout policy and audit logs in mind for any password testing. A valid password does not automatically grant WinRM or administrator access.

05 / Active Directory Certificate Services

Certificate abuse analysis must capture CA configuration, template enrollment permissions, subject naming controls, manager approval, EKUs/application policies, issuance requirements, patch level, mapping, web enrollment exposure, and the principal who can edit each object. Certipy's contemporary research index covers ESC1 through ESC17; these are distinct families with different preconditions, not a single exploit.

Research familiesWhat to investigate
ESC1–ESC4Template request naming, issuance constraints, enrollment agent paths, and writable template configuration
ESC5–ESC8CA/PKI object permissions, delegated CA management and enrollment endpoint authentication surfaces
ESC9–ESC14Certificate mapping, SID security extensions, weak mappings and alternate identity binding controls
ESC15–ESC17Patch-dependent policy interactions, authority permissions and vulnerable service configurations

Use exact installed Certipy help, and distinguish a potential finding from proven user impersonation. Record which certificate authentication endpoint or service was involved and how the issue would be remediated.

06 / Windows Server 2025 and modern defenses

Older AD exploitation guides frequently assume permissive SMB signing, LDAP binds, NTLM relay conditions or RC4-backed ticket workflows. Modern and hardened environments differ. Inspect target builds and policy rather than assuming a technique is available from port state alone.

For each protocol, record the negotiated behavior: SMB signing requirement; LDAP signing and channel binding; NTLM restrictions; Kerberos supported encryption types; certificate binding and KDC policy. These controls may eliminate or materially change a candidate path. Check Microsoft's update notices and installed patch dates when interpreting historical write-ups.

08 / Troubleshooting and evidence

NetExec PKINIT import failure: a missing impacket.krb5.pkinit during LDAP startup is a local Python environment/dependency problem, not proof of a target LDAP issue. Inspect the installed Impacket package inside the NetExec pipx environment before repairing it.

pipx runpip netexec show impacket
bloodhound-ce-python -h
certipy -h

BloodHound collection appears empty: check DNS/DC hostname, domain/realm spelling, permissions, firewalls, machine access, collector version and incomplete graph coverage.

WinRM fails after credential validation: distinguish authentication from authorization; test alternate permitted protocols and the correct host privilege policy.

Kerberos errors: verify FQDN/SPN consistency, KDC selection, clock skew, ticket cache, enctype, realm and trust direction before attempting new tools.

09 / Lab setup: hosts, DNS and Kerberos

NetExec can generate a candidate hosts file from an authorized SMB target or CIDR. This is not authoritative DNS: verify the discovered FQDN and AD DNS domain first. NetExec appends to an existing output file; use a fresh output name or review stale entries on repeated runs.

nxc smb 10.10.11.42 --generate-hosts-file hosts.generated
cat -n hosts.generated

After inspection, back up /etc/hosts and merge only missing, exact lines. This does not automatically resolve conflicting IP-to-name entries:

sudo cp -a /etc/hosts "/etc/hosts.bak.$(date +%Y%m%d-%H%M%S)"
while IFS= read -r line; do
  case "$line" in ''|'#'*) continue;; esac
  grep -Fqx -- "$line" /etc/hosts ||
    printf '%s\n' "$line" | sudo tee -a /etc/hosts >/dev/null
done < hosts.generated

If Kerberos clients need a dedicated realm file, generate it separately, inspect it, and enable it only in the current shell. Check the installed NetExec help, because options may change:

nxc smb 10.10.11.42 --generate-krb5-file krb5.conf
cat krb5.conf
export KRB5_CONFIG="$PWD/krb5.conf"

The local hosts file cannot deliver SRV records. To confirm the domain controller advertised by AD DNS, query the DNS server:

dig @10.10.11.42 _ldap._tcp.dc._msdcs.corp.local SRV +noall +answer
dig +tcp @10.10.11.42 _ldap._tcp.dc._msdcs.corp.local SRV +noall +answer
The optional +tcp form matters in certain controlled pivots. Realms, tickets, time synchronization, DNS discovery and target SPNs all need independent validation.

11 / Fast search and password spraying (authorized labs)

The command generator supports punctuation-insensitive aliases. Searches such as as rep, AS-REP, asrep and GetNPUsers bring up the same roasting technique. Searches for password spray, spray, Kerbrute, ESC13 or hosts identify related recipes. Click the quick-search chips or press / to focus the search box.

What is password spraying?

Password spraying checks one approved candidate password against multiple accounts, instead of checking many passwords against a single account. It can trigger lockouts, alerts, and account disruption even with a single pass. Use only with explicit authorization in a controlled lab.

Preconditions: identify the domain password policy, fine-grained password policies, lockout thresholds and reset window, valid users, permitted source and timing, and the approved password candidate before testing. Never infer that a default of one attempt is guaranteed safe.
nxc smb 10.10.11.42 -d corp.local -u users.txt -p 'LabCandidate1!' --continue-on-success
kerbrute passwordspray --dc 10.10.11.42 -d corp.local users.txt 'LabCandidate1!'

The commands above use example values only; the generator substitutes your actual authorized lab values. Confirm current installed tool help. Success means the respective authentication step passed, not that a host grants administrative access. Distinguish Guest mappings and service authorization from valid domain authentication.

To inspect lockout policy before any spray, find the Review domain password policy recipe. To build usernames, look for SAMR/RID enumeration or Kerbrute user enumeration, respecting authentication and enumeration scope.
